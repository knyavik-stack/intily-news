# INTILY — калибровка editorial scoring 2026-09-06

## Решение

Порог допуска **60.0 сохраняется**.

Снижение threshold до 50.0 было временной диагностической мерой и не является архитектурным решением. Оно показало, что supply можно восстановить, но одновременно подтвердило: шкала score была сжата ниже редакционной границы.

## Фактическая проблема

Production run #326 на первой версии новой policy дал:

- 403 входных материала;
- 273 в диапазоне 0–39;
- 101 в 40–49;
- 29 в 50–59;
- 0 выше 60.

Следующий runtime с временным threshold 50 дал 451 входной материал, 31 в диапазоне 50–59 и 0 выше 60, но 4 новых материала в очередь и 1 публикацию. Опубликованный материал имел score 53.6.

Вывод: discovery работал; проблема была именно в распределении баллов по компонентам.

## Новая модель

Шкала остаётся 0–100. Порог **60.0 не меняется**.

| Компонент | Максимум |
|---|---:|
| AI-релевантность | 25 |
| AI-специфичность | 10 |
| Влияние события | 15 |
| Конкретность события | 10 |
| Практическая ценность | 10 |
| Новизна | 8 |
| Качество источника | 8 |
| Доказательность | 4 |
| Свежесть | 5 |
| Своевременность | 5 |
| **Итого** | **100** |

Дополнительно применяется штраф −6 за низкосигнальные признаки.

## Что изменилось принципиально

### AI-релевантность → AI-релевантность + AI-специфичность

Ранее большая доля score зависела от бинарного `ai_relevant`. Теперь отдельно измеряется плотность конкретных AI-концепций. Это расширяет полезную часть шкалы без ослабления relevance gate.

### Влияние → влияние + конкретность события

Запуск, релиз, исследование, инвестиция, сделка, партнёрство, регулирование и другие признаки события получают собственный вклад. Таким образом, новостная ценность не зависит только от количества общих impact-термов.

### Freshness → freshness + timeliness

Общая свежесть и непосредственная актуальность события разделены. Это даёт более точное ранжирование свежих материалов и не превращает возраст в ложный признак публикации.

### География остаётся отдельной

RUSSIA/WORLD не участвует в editorial score. Региональная балансировка выполняется отдельной publication-priority policy.

## Почему это лучше, чем threshold 50

Threshold 50 делает прохождение проще, но не делает score более информативным. В результате 50–59 превращается в фактическую категорию publishable, хотя шкала формально заявлена как 0–100.

При текущем решении сильная новость должна пересекать 60 **за счёт своих реальных свойств**: релевантности, конкретного события, влияния, практической ценности, новизны, качества источника и актуальности.

Цель — не заранее получить определённый процент выше 60. Цель — получить корректное распределение, при котором:

- слабые материалы остаются ниже 60;
- обычные хорошие новости находятся примерно в зоне 60–84.9;
- действительно исключительные события могут попадать в 85+;
- одинаковые свойства дают одинаковый score;
- нет случайного бонуса региона или искусственных десятых.

## Runtime-критерии приёмки

Следующий production-run считается успешной проверкой калибровки только если:

1. threshold runtime = 60.0;
2. появляются материалы в диапазоне 60–69 и выше, если фактический вход содержит соответствующие события;
3. кандидаты формируются не только из пограничного диапазона 50–59;
4. новые материалы проходят duplicate/history gates;
5. при соблюдении publish interval выполняется Telegram publication;
6. `SCORE_BUCKETS` отражает фактическую шкалу;
7. аналитика использует те же `WEIGHTS` и `THRESHOLD`, что и runtime.

Если после этого сильные реальные события всё ещё массово остаются ниже 60, следующая корректировка выполняется по конкретным компонентам и их фактическому вкладу, а не снижением threshold.

## Техническое состояние

`scripts/intily_scoring_policy.py` — новая feature-level calibration.

`scripts/intily_ai_news_runner.py` — runtime принудительно импортирует `THRESHOLD` из scoring policy и передаёт его в legacy publisher через `IMPORTANCE_THRESHOLD`.

`scripts/intily_policy_analytics.py` — импортирует `THRESHOLD` и `WEIGHTS`, поэтому документационная аналитика не может незаметно разойтись с runtime.

Последний подтверждённый production run до новой feature-level calibration: #327; его результат должен использоваться только как контроль предыдущей версии. Новая модель требует отдельного runtime подтверждения.
