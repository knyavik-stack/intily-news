# Intily — аналитика простым языком

**Дата:** 2026-09-06

## 1. Главное правило

В Intily есть несколько разных чисел, и их нельзя смешивать:

1. **RSS raw** — сколько материалов пришло от источников.
2. **Кандидаты** — сколько материалов прошло текущий математический score, AI-relevance, freshness и первичный semantic dedup.
3. **Новые для очереди** — сколько кандидатов не были ранее опубликованы, не были недавно известны, не находятся в очереди и не являются уже опубликованной/известной semantic story.
4. **Очередь** — сколько новостей сейчас реально можно публиковать.
5. **Публикация** — сколько сообщений реально ушло в Telegram.

Формула потока:

```text
RSS raw
  ↓
score / freshness / AI relevance
  ↓
кандидаты
  ↓
exact + semantic history / queue / known
  ↓
новые для очереди
  ↓
durable queue
  ↓
editorial AI + QA
  ↓
Telegram
```

## 2. Что произошло 2026-09-06

Реальный production run 09:34 UTC получил:

- 154 RSS-материала;
- 31/31 Google News query без ошибки;
- 8 прямых RSS-источников, 7 успешных и 1 HTTP 429;
- 124 материала прошли score;
- 26 кандидатов после quality/relevance/story-dedup;
- 0 новых материалов добавлено в очередь;
- 23 кандидата были уже опубликованными item keys;
- 3 кандидата были заблокированы semantic story history;
- Telegram в этом cycle ничего не публиковал.

Это означает: **поиск новостей в этот момент не был пустым и не сломался**. Discovery нашёл 26 кандидатов. Ноль появился на следующем этапе — при проверке, можно ли считать их новыми историями.

## 3. Почему старое число «19» и новое «0–1» не противоречат друг другу

Зафиксированный production cycle 2026-09-02 действительно получил 169 RSS items и сформировал 19 кандидатов; затем одна история была опубликована, очередь стала пустой. Это было зафиксировано как verification closure.

Важно: **19 кандидатов не означают 19 новых публикаций**.

После публикаций те же материалы могут снова появляться в Google News RSS. Они снова проходят discovery, но затем отбрасываются как уже опубликованные или как та же semantic story. Поэтому снаружи может выглядеть так, будто «алгоритм нашёл 0», хотя на самом деле он нашёл материалы, но правильно не допустил их повторно.

## 4. Обнаруженная ошибка аналитики

В `scripts/intily_ai_news.py` поле `dominant_block` раньше рассчитывалось с включённым `candidate_count`.

Это ошибка: `candidate_count` — размер входа, а не причина отказа.

Исправление применено. Теперь `dominant_block` учитывает только реальные блокирующие причины:

- `published_key`;
- `known_recent`;
- `already_queued`;
- `story_queue`;
- `story_history`.

## 5. Что сейчас действительно является проблемой

### Не проблема

- Google News queries не пустые.
- Google query error rate в проверенных cycles низкий/нулевой.
- Score/relevance pipeline работает.
- AI provider в проверенном окне работает.
- Telegram delivery технически работает.

### Реальная проблема

**Свежего уникального потока недостаточно относительно уже опубликованного потока.**

В последних циклах система регулярно видит кандидатов, но значительная часть — это материалы, которые уже публиковались или относятся к уже опубликованным историям.

Это задача не «починить RSS», а **увеличить разнообразие свежего discovery**.

## 6. Как читать dashboard

### `Candidates`
Сколько историй система считает достаточно качественными для дальнейшей проверки.

Если `Candidates > 0`, discovery работает.

### `Admitted to queue`
Сколько кандидатов действительно новые для текущего состояния канала.

Если `Candidates` много, а `Admitted` мало — проблема находится не в поиске, а в duplicate/history/admission layer.

### `Published`
Реальная доставка в Telegram. Она может быть больше `Admitted` за конкретное окно, потому что публикация может использовать материал, который был добавлен в очередь предыдущим cycle.

### `NO_PUBLISH`
Не всегда ошибка.

- `publish_interval_not_reached` — технически нормальный пропуск, если ещё не наступил следующий слот.
- `empty_queue_after_filters` — кандидаты не дали пригодной очереди.
- `admission_blocked_published_key` — кандидаты уже публиковались.
- `admission_blocked_story_history` — это уже известное событие.
- `PUBLISH_FAILED` — реальная ошибка публикации/редакторского этапа.

## 7. Новая аналитика текущего автозапуска

В `Intily AI News Publisher` после выполнения publisher теперь формируется отдельный русскоязычный блок **«Интеллект поиска — текущий автозапуск»**.

Он показывает именно этот запуск:

- сколько свежих материалов пришло из Google News;
- сколько пришло из прямых RSS;
- сколько отсечено score-фильтром;
- сколько отсечено quality/AI-relevance;
- сколько схлопнуто как одна история;
- сколько осталось кандидатов;
- сколько реально добавлено в очередь;
- какой admission block оказался главным;
- какие поисковые запросы дали больше всего свежих материалов;
- долю каждого запроса в общем Google News потоке;
- какие прямые источники дали свежие материалы;
- были ли ошибки источников.

Этот блок добавляется в тот же GitHub Actions Summary, где находится Production KPI. GitHub официально поддерживает `GITHUB_STEP_SUMMARY` для Markdown-сводок конкретного workflow run. citeturn1search0turn1search1

## 8. История Query + Source Intelligence

История поискового потока хранится отдельно в:

`data/intily-query-intelligence.json`

Ограничение — последние 100 запусков. Это сделано специально, чтобы не раздувать основной `run_history` и не увеличивать state publisher больше необходимого.

Для каждого запроса сохраняются:

- регион;
- текст запроса;
- raw-yield;
- доля запроса в общем поисковом потоке.

Для прямых RSS:

- источник;
- raw-yield;
- ошибки текущего запуска.

Article bodies, API keys и provider secrets в эту аналитику не попадают.

## 9. Почему пока нет искусственной query → admission конверсии

Один и тот же материал Google News может попасть сразу в несколько поисковых запросов. Publisher объединяет общий пул, а затем выполняет score/quality/story-dedup.

Поэтому просто поделить `added` между запросами было бы **ложной точностью**.

Текущая версия честно показывает raw-yield запросов.

Следующий эволюционный шаг — лёгкий `query_id` во время ingestion. Тогда достоверно станет доступна цепочка:

`query → raw → score → quality → story-dedup → admission → publication`

без дополнительных RSS-запросов.

## 10. Принцип развития

Не нужно добавлять десятки RSS-источников вслепую.

Сначала измеряем:

1. какие запросы дают свежий поток;
2. какие источники дают свежий поток;
3. где возникают ошибки;
4. где кандидаты превращаются в новые истории;
5. какие темы реально доходят до публикации.

После этого можно безопасно:

- снижать бюджет шумных запросов;
- усиливать работающие запросы;
- добавлять source-focused `when:6h` / `when:1h` кластеры;
- отдельно оптимизировать WORLD и RUSSIA supply;
- внедрять adaptive query scoring.

## 11. Следующие этапы

После накопления статистики:

1. query provenance;
2. query/source efficiency score;
3. автоматическое снижение бюджета шумных запросов;
4. усиление запросов, которые регулярно дают новые истории;
5. контроль регионального баланса;
6. anomaly detection по supply;
7. topic yield;
8. adaptive scoring только после накопления реальных результатов;
9. adaptive publication timing;
10. Telegram performance — только когда появится надёжный источник фактических просмотров/реакций/пересылок;
11. weekly executive report.

До появления фактических Telegram performance metrics эти показатели нельзя выдумывать.

## 12. Критерий успеха

После накопления статистики владелец должен без просмотра сырых логов ответить:

1. Есть ли сейчас свежие новости?
2. Если есть — сколько проходят score/quality?
3. Если кандидаты есть, почему они не попали в очередь?
4. Какой запрос даёт основной поток?
5. Какой запрос почти бесполезен?
6. Какой RSS-источник реально поставляет материал?
7. Источник сломан или просто сейчас пуст?
8. Intily публикует мало потому, что нет новых историй, или потому что их блокирует dedup/admission?
