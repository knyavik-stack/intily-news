# INTILY — Scoring Calibration 2026-09-07

## Причина изменения

Production run #471 показал реальную проблему математической модели при пороге 60:

- 399 входных материалов;
- 393 (98.5%) были отброшены по score;
- только 6 дошли до кандидатов;
- все 6 оказались уже опубликованными;
- очередь закончилась пустой.

Таким образом, непосредственная причина отсутствия публикации — не отсутствие новостей и не только duplicate protection. Основной bottleneck был **score distribution**. Телеметрия зафиксировала 266 материалов в 0–39, 98 в 40–49, 29 в 50–59 и только 6 в 60–69; диапазоны 70+ были пустыми.

## Что было математически неправильно

Предыдущая модель формально имела 100 баллов, но реальные баллы за многие качественные признаки были слишком малы:

- один конкретный event signal часто давал около 2 баллов;
- один impact signal — 3.75 балла;
- practical signal — 2 балла;
- novelty в основном давала только 2 балла за число;
- freshness/timeliness занимали до 10 баллов, но не компенсировали слабую событийную часть.

Следствие: материал мог быть очевидно важным для редакции, но математически застревал в 50–59.

## Новая модель

Порог **не снижен** и остаётся 60.0.

Модель теперь использует bounded baselines + diminishing returns вместо простого подсчёта совпавших слов.

| Компонент | Максимум |
|---|---:|
| AI-релевантность | 25 |
| AI-специфичность | 10 |
| Влияние события | 15 |
| Конкретность события | 10 |
| Практическая ценность | 10 |
| Новизна | 8 |
| Качество источника | 8 |
| Доказательность | 4 |
| Свежесть | 5 |
| Своевременность | 5 |
| Низкий сигнал | −6 |
| **Итого** | **100** |

### Интерпретация шкалы

- **0–39** — слабый сигнал, упоминание или почти незначимый материал.
- **40–49** — AI-релевантно, но недостаточно значимо для публикации.
- **50–59** — содержательно, однако событие/влияние ещё недостаточно сильные.
- **60–74** — **сильная публикационная новость**: конкретное AI-событие с реальным влиянием.
- **75–84** — крупное отраслевое событие.
- **85–100** — исключительное/каналообразующее событие.

Важно: **60 — это не «редкость» в смысле эксклюзивности.** Редкость обеспечивается отдельными механизмами: semantic story deduplication, source-independent collapse и novelty component. Это предотвращает ошибку, когда обычная, но уникальная новость считается важнее действительно крупного события.

## Что должно давать 60+

Типовой профиль 60+:

1. материал прямо про AI;
2. есть конкретный объект/модель/компания/технология;
3. произошло проверяемое событие: релиз, запуск, сделка, исследование, регулирование, инцидент и т.п.;
4. событие имеет измеримое влияние или практический эффект;
5. источник достаточно надёжный;
6. материал свежий и содержит хотя бы минимальную доказательную базу.

Пример класса 60+: запуск новой AI-модели с конкретными возможностями и влиянием на разработку/бизнес.

Пример класса 75+: крупное приобретение AI-компании, многомиллиардная инвестиция, серьёзное регулирование, значимый security incident или подтверждённый технологический прорыв.

## Что специально не делаем

- не снижаем threshold ниже 60 ради supply;
- не возвращаем случайный Russia bonus в editorial score;
- не используем длину текста как главный источник баллов;
- не считаем большое количество ключевых слов доказательством важности;
- не используем «уникальность URL» как замену уникальности события.

## Регрессионная защита

Добавлен `scripts/test_intily_scoring_policy.py`.

Тесты фиксируют четыре свойства:

- конкретный AI-релиз проходит 60;
- крупная AI-сделка получает высокий tier;
- общий AI-комментарий не проходит 60;
- нерелевантная история не получает AI score.

CI теперь запускает scoring regression tests вместе с media regression tests.

## Production verification

Следующий Cloudflare-triggered cycle должен использовать commit `cbb29b5d9fe840699264dba400b907a87d8a532e` и более новые изменения.

Acceptance criteria:

- `SCORE_BUCKETS` должен показать ненулевой supply в 60+ и желательно появление 70+;
- новые 60+ материалы должны реально попадать в admission, если они не опубликованы/не являются semantic duplicates;
- при наличии eligible item публикация должна происходить при соблюдении Telegram interval;
- для публикаций media KPI должен показывать `photo_sent` или контролируемый `text_fallback` с причиной.
